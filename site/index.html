Herdr Web is a single-operator web client for Herdr, the terminal/agent multiplexer. It flips the model: agents, not terminals, are the primary objects. The home screen lists every agent across your spaces and floats the ones that are blocked to the top — so babysitting a fleet becomes reading a feed, from any device.

the mental model

Status you can read at a glance,
not a wall of terminals.

Herdr already knows which agent is stuck. Herdr Web surfaces that: every agent's state is carried by glyph shape, colour, and a word — never colour alone — and blocked agents sort first. The colours below mean exactly one thing wherever they appear on this page.

blocked — waiting for you working — running now done — finished cleanly idle — nothing to do
browser SvelteKit UI on any device. The inbox, raw panes, diffs, push.
⇄WebSocket
herdr-bridge One Go binary. Embeds the UI, owns one loopback origin, fans data out.
⇄unix socket
Herdr Your running multiplexer. Real RPCs, no screen-scraping.

The bridge is a thin pass-through: the frontend calls Herdr socket methods directly (pane.read, agent.prompt, agent.send_keys) — no terminal emulator pretending to be a web page.

The 95% of agent-babysitting that's just text.

honest scope

Where it fits, and where it doesn't.

If you need a real TUI in a browser tab, this is the wrong tool — and that's fine. Knowing the boundary is the point.

reach for it when you want to
  • Read agent scrollback and see which agent is stuck
  • Answer yes/no and nudge with a one-line prompt
  • Review a diff an agent just produced
  • Get a push the instant an agent blocks or finishes
  • Do all of it from a phone, reliably, every day
reach for something else when you need
  • A full terminal — vim, htop, interactive TUIs
  • A chat or transcript view — live panes are raw terminal only
  • File uploads, multi-host SSH, or a WASM terminal

get running

One command in, running in a minute.

Install the binary, then run it on loopback, as a background daemon, or as a managed system service.

$ curl -fsSL https://raw.githubusercontent.com/sarathsp06/herdrweb/main/install.sh | sh

1 Run it on loopback

herdr-bridge          # serves http://127.0.0.1:7331

2 Or as a background daemon

herdr-bridge -daemon \
  -log-file ~/.config/herdr/herdr-bridge.log \
  -pid-file ~/.config/herdr/herdr-bridge.pid

3 Or as a system service

herdr-bridge -service install   # systemd / launchd
herdr-bridge -service start
herdr-bridge -service status

4 Open it

open http://127.0.0.1:7331   # live spaces, panes, agents

Loopback by design. The bridge binds 127.0.0.1:7331 only. Expose it over a private network such as a tailnet; never bind 0.0.0.0.

On your phone

The UI is an installable PWA. Push needs a secure context, so front the loopback bridge with HTTPS — the easy path is Tailscale. Then Add to Home Screen and enable push per device.

tailscale serve --bg --https=443 127.0.0.1:7331
# open https://<machine>.<tailnet>.ts.net, Add to Home Screen,
# then Settings → Push when blocked (enrol on the phone itself)

from source

A SvelteKit UI baked into a Go binary.

The UI is go:embeded, so make build — not go build — is what refreshes it.

make build     # build the SPA, embed it, compile -> bin/herdr-bridge
make run       # build + run on http://127.0.0.1:7331
make dev       # Vite dev server (HMR), proxies /ws + /api to :7331
make check     # go vet + svelte-check + Go and Vitest tests
cmd/herdr-bridge

Serves the UI, /ws and /api; proxies the Herdr socket.

internal/protocol

Canonical Go types and the Herdr snapshot → UI normalization.

internal/herdr

Socket client: framing, snapshot, event subscribe, reconnect.

internal/server

Hub: one Herdr connection, WebSocket fan-out, periodic re-snapshot.

internal/webui

The go:embed of the built SvelteKit assets.

web/

SvelteKit + TypeScript front end; protocol types mirror the Go structs.
